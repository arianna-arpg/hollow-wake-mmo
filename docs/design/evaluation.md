# Evaluation: tournaments, metrics, bands and trace hashes

Combat is measured, not asserted. The evaluation harness runs seeded duels across pairings of patterns and reports what the simulation's own events say happened: who won and when, what each side dealt, cast and used, and how much of its kit it used and how evenly. Designers keep the pairings and the bands a matched pairing must stay inside as content, gates keep the reports as evidence beside the benchmark rows, and every fight's event log is hashed so a change that should leave the fights alone can show it did.

Code: `src/HollowWake.Core/Evaluation/Tournament.cs` (the runner, the report records and the trace baseline), `src/HollowWake.Core/Evaluation/EvaluationRules.cs` (every rule the harness reads), `src/HollowWake.Core/Content/Kinds/EvaluationKinds.cs` (their validation), `src/HollowWake.Tools/TournamentCommand.cs` (the `hollowwake tournament` command). Rules live in group `evaluation`. The recorded baseline is `experiments/combat-grammar/baselines/standard-duels.json`.

## Rules

Rules group `evaluation` holds every setting of the instrument, and the harness has no value of its own for any of them: the pairings (below), how a duel is staged (`spawn_distance`, how far apart in metres the two bodies spawn, and `factions`, the two factions the sides fight under, a's then b's), a run's defaults (`seeds`, the fights per pairing, and `seconds`, the cap, both used unless the command names others or a checked baseline gives its own), and the bands. A rule that is missing or of the wrong kind stops a run before its first fight, naming it, and validation refuses it first, along with any rule in the group the harness does not read.

## Pairings

Rules group `evaluation` lists the pairings, each written `a:b` with two pattern ids. `proving_pairs` are matched pairings built to be even, the ones a tournament fights unless told otherwise and the ones the bands are for. `standard_duels` are the pairings whose seeded traces are the determinism baseline; `--standard` fights them. `--pairs a:b,c:d` names other pairings for one run and overrides both. Validation refuses a listed pairing not written `a:b` or naming a pattern no definition carries, and a later layer replaces either list like any other rule.

The command checks what it was given before any fight and stops with one line naming the problem, exit code 1: an option it does not know (a misspelled `--check-hash` among them), an option that takes a value with none after it (`--check-hashes` or `--out` last, or followed by another option), an option given twice, a word that is no option's value, a pairing that names an unknown pattern, an empty `--pairs` entry or one not written `a:b`, a `--seeds` that is not a whole number of at least one, a `--seconds` that is not a positive number, a `--check-hashes` file that is missing or not a baseline, an `--out` folder that does not exist, and a rule of group `evaluation` the run reads that content does not write (the staging, the default seeds and cap when the command names none, and with `--bands` the bands). So a gate that misspells its option fails instead of running unchecked. Once it has fought, the command exits 0 when everything it was asked to check held, and 1 when a checked hash changed, a band broke under `--bands`, or the simulation logged an error.

## What a fight is

A fight is one pairing in a fresh arena (`ZoneBuilder.CreateArena`) seeded from the pairing and the fight's index, the two bodies spawned `spawn_distance` apart under the two `factions` (each added to the registry, hostile to the other, only where the registry lacks it; a faction content defines is used as content defines it), ticked until one of them dies or the cap in seconds runs out. The fight ends with the tick in which a body died, and the body still standing after that tick wins. When both bodies are dead after that tick, however they fell in it (one blow killing both, or each falling to the other), it is a double knockout: a draw, like a fight that reaches the cap with both standing, but one that ends before the cap. Like every draw it counts toward the draw rate and not toward the time to kill. Neither side is structurally first. The body spawned first is created first, and so thinks and acts first on every tick the two share, so the side spawned first alternates with the fight's index: a on even indices, b on odd ones. The two spawn mirrored about the arena's origin, a to the west, and each is then turned toward the other, so neither starts facing away (hit angles read facing). `hollowwake fight` stages a duel the same way (`Tournament.Spawn`).

What the harness reads from a body is this and no more: its pattern's name; its book, for the kit (the seats, and the converts and combo chains that map a face to its seat); its stats, for life left (life over its maximum); its life and position, for the trace's last line; and, for crediting, the owner links the kill-credit chain follows. The one thing it writes to a body is its facing at spawn. Every other number comes from the events the simulation publishes: `DamageDealt`, `Healed`, `StatusApplied`, `WeaveCast`, `WeaveReleased`, `WeaveInterrupted`, `EntitySpawned`, `EntityDespawned`, `EntityDied`, and the cast presentation events (`CastPresentationEvent`), which the harness turns on for its arenas; they only publish, so the fight is the same with them on or off. The mechanisms a side used are those of the weaves its uses cast, as those events carry them. The same seed gives the same fight on the same platform, so a report repeats exactly there and a change in it means a change in content or code.

A side is its body and whatever it owns. Damage, hits, casts and statuses by its minions, constructs, projectiles and fields are credited to it up the owner chain, the way kill credit is (`DeathService.CreditTarget`), so a summoner's kit is measured as its kit. Damage, hits, crits and statuses are a side's work only when the side that owns their target, found up the same chain, is another one (or none). An event whose source and target belong to one side is that side's own doing to itself and is booked apart, per side, as its self-sourced damage and statuses: a buff it lays on itself, a pool of its own breaking and re-arming, and a status that ticks on after its applier is gone, which the simulation then sources from its bearer, so an imp's burn still ticking once the imp is replaced reads as the burned body's own, never as damage that body dealt.

Its kit is its body's: the seats in the body's book, a seat being one weave of the book with its own cooldown, uses and faces. A use is a press or a trigger that starts a seat's cast, counted once however many beats, faces or releases it resolves in, against the seat that owns it: the seat holding the weave cast, or the seat whose convert or combo chain put it on as a face, so a chain's third press counts for the chain's seat and a channel held for a dozen beats is one use. The harness reads a use from the cast's identity (`CastPresentationEvent.CastId`), which the runtime gives once per press or trigger and every phase of that cast carries: the first sighting of an identity is the use. `WeaveStarted` cannot serve, since an instant press resolves without one, nor `WeaveCast`, which fires on every beat and names the face. Coverage is the seats used over the seats in the kit, never above one since every use is counted against a seat of the book, and spread is the effective number of seats used, the exponential of the entropy of the uses over the seats: one when every use went to one seat, the number of seats used when they shared the uses evenly. A minion's presses are its own: they count in its side's casts, not as uses of its owner's seats. Two seats holding the same weave read as the first of them.

## What a report holds

Per fight: its outcome, when it ended, its trace hash, and per side the damage dealt, hits and crits (a hit is any application of damage that was not evaded, blocked ones included), casts (every `WeaveCast` of the side, a channel's beats and releases each one), uses, the size of its kit, its coverage and spread, the seats it used, the weaves its uses cast (faces included) and their mechanisms, the statuses applied, its self-sourced damage and statuses, and the fraction of life left; and the warnings and errors the simulation logged while it ran, in order, since every arena writes to a log that keeps them (`CountingSimLog`). Per pairing: its trace hash, win rates for each side and the draw rate, the median and quartiles of time to kill over the fights that ended, each side's coverage and spread averaged over its fights, the union of seats and mechanisms each side used, each side's self-sourced damage summed over its fights and the self-sourced statuses it bore, and the bands it broke. Per run: a trace hash over its pairings. The whole report serializes to JSON (`--out`), so a pull request can keep it under the evidence folder. Every number the harness writes, in the table, the breaches, the trace and the seed texts, is written in the invariant culture by the library itself.

## Replaying a fight

Every fight records its seed text (`Seed`, written `tournament:a:b:i`) and the tick it ended on (`EndTick`), with `Seconds` that tick's time to the millisecond. `hollowwake fight a b --seed tournament:a:b:i --seconds S` replays fight `i` of pairing `a:b` exactly up to its first death: the fight command seeds its arena with the same text, reads the text back to the fight's index so the same side spawns first, and stages the duel with `Tournament.Spawn`. Give it a cap of at least the fight's `Seconds`, since its own default is shorter than a tournament's; past the first death it keeps ticking where the tournament stopped. A test replays fights of both spawn orders this way and requires the same end tick.

## What goes wrong

A fight on content the simulation could not run is not a measurement, and it must not read as a quiet fight. A weave that failed to compile, an unknown behavior, a component that failed to bind and a system that threw all reach the simulation's log, so the table names each distinct warning and error under its pairing with how many of its fights logged it, a seat whose weave never compiled still counts in its kit (unused, never an empty kit), and an error fails the command, which names the first.

## Bands

Rules group `evaluation` holds the bands a matched pairing must stay inside: `ttk_min` and `ttk_max` for the median time to kill, `win_rate_ceiling` for either side's share of wins, `draw_ceiling` for the share of fights that end in a draw, and `coverage_floor` for the coverage each side must reach, the share of its kit's seats it uses, averaged over its fights. With `--bands` the command names every breach and fails. Bands are for pairings built to be even, such as the proving pairs; an uneven pairing is measured but not banded.

The harness has no band of its own: it reads each from content with no number to fall back on, and a band that is missing or not a number stops the run, naming it. Validation refuses such content first: every band must be written and a number, `ttk_min` at least zero and `ttk_max` at least `ttk_min`, the ceilings and the floor shares from 0 to 1, and every rule in the group must be one the harness reads, so a misspelled band is named rather than ignored. A report says whether it judged anything: `BandsChecked` is true and `Bands` holds the bands it judged by when the run checked them; otherwise `BandsChecked` is false and `Bands` and `Passed` are null, because a run that checked nothing passed nothing.

## Trace hashes

A fight's hash is the 64-bit FNV-1a hash (`Rng.Hash64`) of its ordered event log, written as sixteen hex digits. The log holds one line per event in the order the simulation published it, each opening with its tick: every `EntitySpawned` (what and where, the two bodies included) and `EntityDespawned`, every `WeaveCast` (caster, weave, target, aimed point), every `WeaveReleased` (caster, weave, mode, reason, whether it fired, held, fill, stage) and `WeaveInterrupted` (caster, weave), every `DamageDealt` (source, target, amount, and whether it was a crit, evaded or blocked), every `Healed` (source, target, resource, amount), every `StatusApplied` (source, target, status, stacks, duration) and every `EntityDied` (body, killer), then a last line with the outcome and each body's life and position. A fight that reaches the cap with both standing still moves its hash when they end it differently, by regeneration, leech or a step: whatever changes a body's life or place shows in that line. The two bodies are named `a` and `b`; anything else is named by its pattern, or its name when it has none (a projectile, a field), marked with the side that owns it. So the hash follows what the fight did, not how the world numbered its entities. Amounts, durations and positions are written to hundredths in the invariant culture, so the text does not depend on the host's culture. A hash repeats exactly on the platform it was recorded on. Another platform may round floating point differently (a sine, a square root, a fused multiply and add), and a difference of one hundredth anywhere moves the hash, so a hash that differs there is a finding to record, not a regression and not a reason to rewrite the record (see the baseline below).

A pairing's hash folds its fights' hashes in seed order, and a run's folds its pairings' in the order they ran. A pairing's hash depends only on its patterns, the content, the code, the platform, the number of seeds and the cap, never on what else ran in the same process.

## The determinism baseline

The standard duels' hashes are recorded in `experiments/combat-grammar/baselines/standard-duels.json`: the seeds and the cap they were fought with, the platform they were recorded on (the runtime's identifier, such as `win-x64`), and each pairing's hash keyed `a:b`, sorted so a review can diff it. `--hashes` prints the hashes after the table, and with `--out` writes them in that shape instead of the full report. `--check-hashes FILE` fights the selected pairings against such a file, with its seeds and cap unless the command names others, then prints `hashes: identical` or one line per difference (a pairing whose hash changed, one the file does not hold, one it holds that the run did not fight, a different number of seeds or cap) and fails.

A change that should not move a fight checks the standard duels against the baseline and stays identical. A change that does move one regenerates the file in the same pull request and names the change, and the pairings it moved, in its review record. A test holds the committed file to the code (`TheCommittedBaselineHoldsOnItsPlatform`): on the platform the file names it fights the standard duels with the file's seeds and cap and requires every hash identical; on any other it requires only that two runs hash the same, and prints how the hashes differ from the file as information. A run on another platform that differs from the file is a finding to record, not a reason to overwrite it; `--check-hashes` says so when the platforms differ.

## Using it

```bash
dotnet run --project src/HollowWake.Tools -- tournament                                   # the proving pairs, with the seeds and the cap rules group evaluation gives
dotnet run --project src/HollowWake.Tools -- tournament --pairs wolf:hob,proving_reaver:proving_bulwark --seeds 20 --seconds 45 --bands --out report.json
dotnet run --project src/HollowWake.Tools -- tournament --standard --hashes --out experiments/combat-grammar/baselines/standard-duels.json   # record the baseline with those seeds and that cap
dotnet run --project src/HollowWake.Tools -- tournament --standard --check-hashes experiments/combat-grammar/baselines/standard-duels.json
dotnet run --project src/HollowWake.Tools -- fight proving_reaver proving_bulwark --seed tournament:proving_reaver:proving_bulwark:1 --seconds 60   # replay fight 1 of a pairing
```

A gate on a content or AI change runs the proving pairs with bands, keeps the JSON, and compares the mechanisms each side used before and after: a doctrine or a weave that never shows in a report is not proven to work. The report is not a playtest: a human rubric and recorded sessions say whether the fights are good, the harness only says whether they stay inside what the designers wrote down.
