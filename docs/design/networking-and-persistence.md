# Networking and persistence

The checkout's play helper publishes the server into its private `artifacts/playtest/server/` runtime and uses an owned lease for graceful shutdown. This keeps normal solution builds available while playtesting. Shutdown unhooks process events and joins the lease monitor before disposing cancellation state.

## Sessions

The pure .NET host's local-play orchestration flags are `--bind`, `--websocket` and `--lifetime-file`. The last watches a checkout-owned lease file, updating its heartbeat while present and requesting the existing save/shutdown path when removed. These are host lifecycle controls, not game messages; ordinary server runs need no lease. The local helper never terminates unrelated processes to free a port.

A connection becomes a session. `hello` negotiates the protocol and optional features: a hello may list the `features` the client understands, and the welcome lists the ones the server granted. Both lists are absent when empty, so a hello without features gets the plain protocol, exactly as before features existed. `entity_delta` (see Deltas below) and `interface` (see Interface states below) are such features. `login` authenticates (development: any name; token mode: a shared secret) and returns the account's characters and the available callings; `create_character` and `select_character` manage characters; after `enter_world` every in-world message becomes an intent queued on the player entity and validated by the simulation. Pings answer with server time. Chat broadcasts within the zone.

## Zones and interest

The optional `hit_bodies_v2` hello feature grants a reliable `hit_bodies` catalog immediately after welcome, before world entry. It contains simulation profile ids, aim indices and volume recipes normalized on all axes by body height. The earlier unmerged v1 radius-normalized catalog is not granted. Only diagnostic views receive the additive `hit_body` profile id. Height, position and yaw resolve anatomy; radius still draws clearance. Profile changes participate in snapshot fingerprints and deltas; a delta's empty string clears the profile. Clients request the catalog only when the developer option is enabled before connection, and clear it when reconnecting. Enabling the option during a session requires reconnecting. A missing catalog or unknown primitive cannot certify a damage outline and must show it as unavailable. The catalog is immutable for the connection's content; live content replacement requires reconnecting.

The independent `projectile_slabs_v1` hello feature identifies projectile height as the full collision slab height centered on the flight position. Current clients request it for ordinary rendering, without requesting the anatomy catalog. Older servers that do not grant it retain legacy visual thickness. Movement radii keep their existing wire meaning.

The optional `cast_cues` feature adds reliable, correlated lifecycle events and ongoing-preparation reconstruction on spawn. The phase, sequence, interest and reset rules are specified in [cast-presentation.md](cast-presentation.md); it carries no client visual recipes or prospective hit regions.

A `ZoneInstance` ticks its simulation and, at the snapshot rate (`snapshot_rate`), asks its `SnapshotBuilder` what each session needs to hear about the entities within its interest radius (a column: `interest_radius` on the ground plane and `snapshots.interest_height` up and down). Each session keeps a `SnapshotView` of what it has been told: the entities it knows, whether each is static, the fingerprint of the state last sent, and when each is next due a refresh. The rule is to send what changed and nothing else. Simulation events become combat events, notices, quest offers, crafting challenges and results, and intent rejections for the sessions that can see the entities involved.

**Spawns and despawns.** An entity entering interest is spawned with its full state; one leaving it, or destroyed, is despawned. A spawn for a key the client already knows replaces that entity's state.

**Effective allegiance.** The existing entity `Faction` field is resolved through combat relations, including a minion's living owner. Its snapshot fingerprint uses that same resolved value, so an owner's allegiance change updates its summons without changing their native pattern faction. Contact marks therefore agree with server targeting. This adds no wire fields or feature negotiation.

**Static entities.** An entity with none of the components that move it or change what a client sees (stats, motion, projectiles, fields, tethers; more can be registered with `Snapshots.MarkDynamic`) is static: flora, props, markers, founts, drops and telegraph marks. It is spawned once with `static: true` (the field is absent when false) and never appears in an update. Static entities are re-verified on the refresh cadence: one that died is despawned, and one that changed or became dynamic is spawned again.

**Deliveries as drawn.** Every projectile, field, tether and telegraph mark carries the registered hit shape it is drawn as (`shape`, by the same name the hit tests use) and its `shape_size` resolved by the server, the shape's defaults applied, so a client never needs the shape table: radius and width in world units, the angle in radians, `inner` (the radius left empty at the anchor) in world units, and a bowed shape's `curvature` in radii. `heading` is the shape's facing (a client without one falls back to the yaw) and a flight's `spin` how far its shape has turned from it; a flight sends its velocity in the velocity fields, which it keeps outside motion. A plain flight is a circle of its collision radius. A tether is drawn as a bar laid along its line: its transform sits at the line's midpoint with half the length as its radius and its yaw along the line, so its heading is a quarter turn from the yaw and its width is the tether's. A body with a lifetime (a telegraph mark, a timed summon) carries `until`, the server time it lands or ends; a telegraph mark (look `telegraph`, a circle of its radius) is static, spawned once with it. A delta never clears a heading or a spin and never moves `until`: the full state goes instead.

**Updates.** `entity_update` carries only the dynamic entities whose state changed since the state last sent to that session. Change is judged by a fingerprint of everything the state carries: position, size and velocity to the centimetre, yaw to a hundredth of a radian, resources in steps of `snapshots.resource_step` of their maximum, cast progress in `snapshots.cast_steps` steps per cast, and every other field exactly. Values on the wire are positions, sizes and velocities to the centimetre, yaw to a hundredth of a radian, resources to a tenth and cast progress to a hundredth. An entity that does not change is not sent, so a standing player hears nothing about itself, and an update says nothing about entities it does not list. Each state is as of the `server_time` of the message that carried it.

**Refreshes.** Unreliable transports may drop updates, so an entity that changed since its last refresh is sent in full on its refresh cadence (`snapshots.refresh_seconds`), including once after it goes quiet, and every known dynamic entity is sent in full on the sweep cadence (`snapshots.sweep_seconds`). Cadences are staggered by entity key, so refreshes spread across snapshots.

**Deltas.** A client whose hello lists the `entity_delta` feature gets changes as `entity_delta` messages instead of in `entity_update`: each delta carries the key and only the fields that changed (absent means unchanged). Strings that can become empty (pattern, look, faction, rarity, interactable, casting) arrive as "" when they do; flags and statuses arrive whole when they change; resources and maxima carry only the entries that changed. Full states still arrive in `entity_update` on refreshes and when a delta cannot express a change (the set of resources changed). A delta for a key the client does not know is ignored; the next refresh repairs it. `EntityDelta.ApplyTo` is the reference for applying one. A client that does not ask for deltas gets full states only.

**Self state.** The owner's view of their character (level, attributes, resources, weaves with cooldowns and costs, bag, equipment, currency, quests, reputation, holdings) is checked every `snapshots.self_seconds` and sent when its fingerprint changes, and at least every `snapshots.self_max_seconds`. The fingerprint covers what the message reads, with cooldowns counted down in steps of the check interval so a cooldown still visibly ticks; attribute values are reused while the attribute set is unchanged.

**Interface states.** A client whose hello lists `interface` draws the interface of [ui.md](ui.md). Its self states also carry the cluster's fields (reserved amounts, the pools before life and their states, the hero's statuses, the cast, charges and recent stamps), and on the same cadence it is sent the `inventory_state`, `weave_slots`, `passive_state` and `page_state` messages whenever each one's fingerprint changes, and once on entering a zone. Fingerprints are built over what each message reads without allocating: statuses count by when they end and cooldowns by when they are ready, so timers running down change nothing, and weave previews follow the hero's numbers at most every `snapshots.preview_seconds`. World panes (`dialogue_state`, `vendor_state`, `station_state`) answer the hero's interactions and reach every client. One read has a side effect: a weave's use bank (and a converted face that reads it) is brought up to date in the slot state when it is read, as the runtime does whenever it reads it; the value is the same closed form whenever that happens, and the read is made only for slots whose weave has a bank or a convert. A client that does not list `interface` gets self states exactly as before and none of the rest.

**Cost.** Building snapshots never changes the simulation, so each entity is fingerprinted and captured at most once per tick however many sessions see it. Sessions count the payload bytes they are sent, the part that is snapshot traffic (split into changes, spawns and despawns, and self states), and the snapshots built for them; leaving a zone logs each per snapshot. The benchmark and tools can drive a `SnapshotBuilder` with their own views the same way a zone does.

**Settings.** The `snapshots:` section of config/server.yaml (`SnapshotSettings`) tunes precision and redundancy; every session's view is given these settings when it connects. Coarser steps send fewer changes at the cost of how closely a client tracks values between them.

| Setting | Default | What it tunes |
|---|---|---|
| `refresh_seconds` | 2 | A changed entity is resent in full once it goes quiet; static entities are re-verified |
| `sweep_seconds` | 10 | Every known dynamic entity is resent in full whether or not it changed |
| `self_seconds` | 0.5 | How often the self state is checked for change; cooldowns count down in these steps |
| `self_max_seconds` | 2 | The longest a client goes without a self state |
| `resource_step` | 0.02 | Resources count as changed in steps of this fraction of their maximum, no finer than a tenth of a point and no coarser than this fraction of a hundred points |
| `cast_steps` | 5 | Cast progress counts as changed in this many steps per cast |
| `interest_height` | 64 | How far above and below a player interest reaches |
| `preview_seconds` | 2 | For interface clients, the shortest time between weave preview refreshes when only the hero's numbers changed |

Walking out of a zone or using a portal transfers the player: the sheet is captured, the entity despawned, the neighbor zone created if needed, the entity materialized there, and the client told to re-enter. Zones with no players unload after a timeout (the start zone stays).

## World events

On an interval the host picks a loaded region and a weighted event definition, adds its generation overlay over the region for the event's duration, and tells everyone. Active events and their end times persist.

## Transports

`ITransport` raises connected, received and disconnected from any thread into a thread-safe inbox drained on the world thread. TCP frames messages by length; loopback runs in process for tests; RakNet (BRUTAL host) sends reliable-ordered for everything but entity updates and deltas, which go unreliable-sequenced (the refresh cadence repairs what is dropped). WebSocket (`HttpListener`, port `websocket_port`, path `/ws`) carries one whole message per binary frame with no length prefix; text frames and messages over the serializer's size limit close the connection, and a client that falls behind loses queued entity updates and deltas before anything else, which the refresh cadence repairs the same way. The same listener serves the built web client from `web_root`, falling back to `index.html` for routes and never serving outside the root or dot files, and answers a plain GET on `/ws` with a JSON description of the service so a page it serves can find it. `CompositeTransport` puts several transports behind one, re-numbering connections so session ids stay unique; the pure host runs TCP and WebSocket that way unless `websocket_enabled` is false.

## Terrain on the wire

Entering a zone sends `chunk_data` for every chunk the simulation has modified. `request_chunk` returns any chunk within `chunk_request_radius` chunks of the player (farther requests get a `chunk_out_of_range` error, so a client cannot make the world thread generate and keep land nobody is near); the web client builds all of its terrain this way. `chunk_data` carries heights, cell flags, the interned surface tag strings, layers and the chunk's water level.

## Persistence

Store interfaces: accounts, characters, world (holdings, events, the item uid counter) and modified chunks. The JSON file implementation writes one file per record under the data directory with atomic replace. Autosave runs on a timer and on shutdown; characters save on leave and on autosave. A database implementation of the same interfaces is the planned next step.

A character's sheet holds its position, level and experience, passives with the options picked, points granted, realms opened and refunds made, the weave book and the rack (codices and stones by seat), the bag with each item's cell, worn equipment, the wallet, quests, story flags, discoveries, reputation, and its own container boards with the stash pages bought. The account holds the account's boards (its vault: the reliquary, the account stash and its pages bought). The character store fills the sheet's vault from the account when the character loads and writes it back to the account when the character saves; the character's own file never holds it, and a sheet that came without one never writes it. Loading is forward-compatible: a field a save lacks takes its default, an item keeps its cell while it fits there and otherwise finds another or waits without one, and items of a board content no longer has are kept (the character's in the bag's overflow, the account's as they were).
